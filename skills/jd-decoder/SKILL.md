# JD 拆解：看出岗位背后真实的问题

## 这个 Skill 解决什么问题

读 JD 最常见的做法是从头读一遍，看自己符不符合要求。这样读不出任何有用的东西，因为每份 JD 都写得差不多。

更有价值的是判断这些要求背后反映了什么问题：团队为什么招人，这个岗位每天真正在处理什么，面试官最担心招错什么样的人。想清楚这几件事，后面不管是决定投不投、改简历还是备面试，心里都更有底。

## 输入

必需：**岗位 JD**（粘贴文字或截图均可）。

可选：公司名称、用户的目的（判断要不要投、改简历、写求职信、备面试）、用户自己的目标和顾虑。

处理规则：
- 没有 JD 就先请用户贴出来，不要凭岗位名称猜。
- 用户没说目的就直接拆，在结尾按几种常见目的给出下一步建议，不要先追问。
- JD 是截图时先读出文字内容再分析。
- 用户给了多份 JD，见"多份 JD 对比"。
- 全程使用用户的语言。

## 原则

- **推断要标注，并给置信度。** JD 写明的是事实，从措辞推出的团队处境是推断。推断可以大胆，但必须让用户分清，因为用户可能掌握你不知道的信息（比如认识在职员工、了解团队背景）。
- **信号是线索，不是结论。** 下面的对照表用来启发思路。判断要依据整份 JD 的上下文，同一个词放在不同岗位里意思可能不同。
- **不替公司下结论。** 红旗只说"可能"并建议在面试中确认，不要对用户断言"这家公司有问题"。
- **不编造公司信息。** 公司的业务、规模、文化、近期动态，只用用户提供的或搜索得到的内容。只有一份 JD 时，分析仅限 JD 本身能支持的范围。

## 拆解步骤

### 1. 扫描 JD 的结构和频率

- 哪些词或意思被反复提到。同义表达也算，如"推动""落地""闭环"是同一类。
- 哪些要求写在最前面，或用了"必须""优先""负责"这类强措辞。
- 职责部分和要求部分都出现的主题，置信度最高，它们几乎一定是岗位的重心。
- "加分项"和"优先"的内容，权重低于"必须"，可以单独列出。
- 通篇套话、没有具体职责对应的形容词（如"积极向上""有责任心""良好的沟通能力"），降低权重，不要围着它们分析。

### 2. 把措辞翻译成信号

先找到措辞，再推断团队可能的处境。

| JD 里的措辞 | 可能反映的情况 | 面试官会关注 |
|---|---|---|
| 快节奏、自驱力、能独立推进 | 团队没有太多时间手把手带新人，需要入职后快速上手的人 | 能不能在信息不完整时自己找方向并跑起来 |
| 跨部门沟通、推动落地 | 日常工作是协调不同部门之间的信息、资源和冲突，很多事不是你说了算 | 没有职权时如何影响别人、如何处理分歧 |
| 从 0 到 1、搭建体系 | 业务早期，流程和规范缺失 | 能不能自己定义问题、做取舍 |
| 数据驱动、分析能力 | 决策需要依据，现状可能偏凭经验 | 如何用数据发现问题并推动改变 |
| 多项目并行、抗压、灵活应变 | 优先级常变，人手紧 | 如何排优先级、被打断后怎么办 |
| 优化流程、提升效率 | 现有流程有明显痛点 | 有没有做过改进并量化结果 |
| 对接客户、高标准交付 | 有外部压力，容错低 | 如何管理预期、处理投诉或延期 |
| 负责人意识、owner、端到端 | 职责边界不清晰，出了问题要自己兜底 | 超出职责范围的事情怎么处理 |
| 有行业或业务经验优先 | 希望缩短培训期，尽快进入业务 | 对业务的理解有多深 |
| 带团队、管理经验 | 可能要承担管理或招人，也可能只是头衔需要，要确认是否真有下属 | 管理经验的真实程度 |

### 3. 回答三个问题

- **他们为什么要招人？** 新增业务、补位、替换、团队扩张，从措辞和岗位性质里找线索。
- **这个岗位最需要解决的问题是什么？** 用一句话概括，要具体到这个岗位，放在别的岗位也成立的话不算数。
- **如果我是面试官，我最关注候选人哪些能力？** 按重要性排序。

### 4. 找出模糊、矛盾和红旗

JD 里没写清楚的地方，往往是面试中最值得确认的。关注：

- **职责过多过杂**：一个岗位同时覆盖几类差异很大的工作，可能是一人多岗或岗位定义不清。
- **强度类措辞没有场景**：反复强调"抗压""能适应高强度"，但没写具体业务场景，工作强度可能偏高。
- **要求与岗位不匹配**：年限、学历或技能要求明显高于职责内容，或者岗位名和实际内容对不上。
- **关键信息缺失**：没有写业务方向、团队规模或汇报关系。
- **前后矛盾**：比如一边写"独立负责"，一边写"在上级指导下完成"。

处理方式：把每一条红旗转成一个可以在面试里问的问题（最多 3 个），比如"这个岗位目前和哪几个团队对接最多？"。这些问题同时也是很好的反问素材。

## 输出格式

使用下面的结构，除非用户要求其他格式。

```
# JD 拆解：[公司/岗位名]

## 一、岗位真实问题
一句话。

## 二、核心要求 Top 3~5
| 要求 | 依据 | 背后的信号 |
|---|---|---|
| ... | 明说 / 推断（置信度：高/中/低）+ 一句依据 | ... |

## 三、面试官关注点
每项核心要求配一个"面试官最可能问的问题"。

## 四、模糊与待确认项
最多 3 条，每条说明为什么值得确认，并给出可以问的问题。（没有明显红旗就写"未发现明显疑点"，不要硬凑。）

## 五、接下来可以怎么用
按用户目的给出 2~3 条建议，见下。
```

**"接下来可以怎么用"按目的给建议：**
- **判断要不要投**：结合第四部分，指出这个岗位对什么样的人最合适、对什么样的人风险较大，把决定权留给用户。
- **改简历**：指出哪几项核心要求应该在简历里前置和强化。只建议调整重点和表述方式，不要建议加入用户没做过的经历。
- **写求职信**：可以围绕"岗位真实问题"来组织，而不是复述 JD。
- **备面试**：提示可以提供简历，继续把要求转成自己的证据，并准备高频问题的回答。（可以使用 interview-prep。）

篇幅控制：重点是判断，不是复述。核心要求最多 5 项，红旗最多 3 条。用户读完应该能用一两句话说出"这个岗位到底要解决什么问题"。

## 多份 JD 对比

用户给了多份 JD（同一公司的不同岗位，或不同公司的类似岗位）时：
1. 每份单独给出"岗位真实问题"和 Top 3 要求，保持简短。
2. 然后做一张对比：共同要求（说明这类岗位的通用能力）和差异点（说明各自的侧重）。
3. 如果用户在选择投哪个，只给对比和判断依据，不替用户做决定。

## 交付前的自检

- [ ] "岗位真实问题"具体到这个岗位，不是放在别的岗位也成立的泛泛之谈
- [ ] 每项核心要求都标注了"明说"或"推断"，推断有置信度
- [ ] 套话类要求已经降权，没有占用 Top 5 的位置
- [ ] 没有对公司下断言，没有编造 JD 以外的公司信息
- [ ] 红旗都转成了可以在面试中确认的问题，且不超过 3 条
- [ ] 改简历的建议没有鼓励用户加入没做过的经历
