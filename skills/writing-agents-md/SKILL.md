# AGENTS.md / CLAUDE.md 编写指南

这个文件是 Agent 的入职文档，不是知识库。它的价值由信噪比决定，不由长度决定。

## 三个前置认知

**这是投入产出比最高的一个文件。** Agent 每次开会话都是失忆的：昨天交代的技术栈、测试命令、绝对不能碰的目录，今天一概不知道。`AGENTS.md` / `CLAUDE.md` 是唯一能让它每次开工就“记住”的东西，而且影响你跟 Agent 的每一次交互。一条缺失的规则让 Agent 每天多犯一次错、你多花五分钟纠正，一年就是三十个小时；把这条规则写清楚只要一分钟。

**它已经是跨工具标准。** AGENTS.md 已由 OpenAI 捐给 Linux Foundation 旗下的 Agentic AI Foundation，与 MCP 同一个基金会管理，Codex / Cursor / GitHub Copilot / Gemini CLI 均原生支持。在这里练出来的功夫，换任何工具都不白费。

**往启动上下文里塞得越多，越不听话。** 这是反直觉的部分，也是本 Skill 存在的理由。

## 两种崩坏方式

OpenAI 曾用 Codex 从零搭一个内部产品（百万行代码、零行手写、三个工程师五个月、1500 个 PR），初期把所有规则塞进一个巨型 `AGENTS.md`。他们自己的结论是 "it failed in predictable ways"。原因只有两条。

### 一、注意力稀释

上下文窗口有限。塞两百条规则进去，Agent 真正该关注的东西——当前任务、相关代码、要参考的文档——反而被挤到角落。更麻烦的是，两百条规则全都摆在“开机自启动”的位置，对 Agent 来说等于**没有优先级**：它分不清哪条是此刻必须遵守的、哪条完全没用。

行业实测的经验值是，前沿模型能可靠遵循 150–200 条指令，而 Claude Code 自身的系统提示已占掉约 50 条，留给项目的只有 100–150 条。超过之后发生的事很反直觉：**受影响的不只是新加的规则，是所有规则的遵循质量一起下降。**

> 这是经验值不是硬规格，但方向可靠：预算有限，且超支是全局性贬值，不是局部损耗。

所以行数上给自己立个规矩：**300 行以内，能更短就更短**。参照系：OpenAI 改写后的 `AGENTS.md` 约 100 行，Boris Cherny 的一百多行。

### 二、上下文腐烂（Context Rot）

代码天天变，架构在演进，但那个几百行的文件没人想更新。写的时候人人都觉得“以后会维护的”，三周之后它就成了屎山。Agent 不知道哪些还有效、哪些早就过时，人也搞不清。

到这个阶段，文件从资产变成负债：它还在每次会话里消耗上下文，但提供的信息已经开始出错。而过时的规则会被 Agent 当成事实执行。

### 共同根源

两条都是同一个错误：**试图在启动时把所有信息一次性灌给 Agent。**

所以解法不在“删信息”，而在“改时机”——信息本身没错，错在它出现在每一轮对话里。

## 一条判断标准

每次想往启动上下文里加东西，先问一句：

> **这个信息是每次会话都需要，还是只有特定任务需要？**

每次都需要 → 留在 `AGENTS.md`。只有特定任务需要 → 放进 `docs/` 或 `.claude/rules/`，这里只留一句“什么时候去读它”。

这一条筛掉的东西通常比你预想的多。剩下的继续过三个筛子：

| 筛子 | 问法 | 不合格的例子 |
|---|---|---|
| 猜得到吗 | 不看这个文件，Agent 能从代码里推断出来吗？ | “这是一个 Next.js 项目” |
| 工具能管吗 | 已经有确定性工具在管吗？ | “用 2 个空格缩进” → 交给 Prettier |
| 可执行吗 | 它读完知道下一步做什么吗？ | “注意测试性能” |

三关都过，才值得占指令预算。

## 目录，不是百科全书

答案是**渐进式披露（Progressive Disclosure）**：Agent 从一个小的、稳定的入口开始，需要时才去读更深层的信息，而不是一开始就被所有东西淹没。

这个模式在四个互相独立的系统里各自收敛到了同一个结构：

| 系统 | 稳定的入口 | 按需加载 |
|---|---|---|
| 项目指令（OpenAI） | 约 100 行的 AGENTS.md | `docs/` 里按主题拆分的文档 |
| 个人知识库（Karpathy 的 LLM Wiki） | 约 2500 字符的 `index.md`，每页一行摘要 | 顺索引读页面；几百页规模下不需要向量数据库，索引 + `grep` 就够 |
| 技能加载（Claude Code Skills） | 每个 Skill 的名字 + 一句话描述，约 100 token | 判断相关才加载完整内容和脚本 |
| 工具加载 | 低频工具只留一个名字 | 需要时现场取回完整定义 |

放到你的项目上：`AGENTS.md` 只干一件事——**告诉 Agent 它需要知道的东西在哪里**。

## 放哪里：四层

| 层 | 位置 | 作用范围 | 放什么 | 提交到 git |
|---|---|---|---|---|
| 1 全局 | `~/.claude/CLAUDE.md` | 所有项目 | 个人偏好（“回复用中文”） | 否 |
| 2 项目根 | `./AGENTS.md` | 本项目，团队共享 | **全部项目规则写这里**，主战场 | 是 |
| 2 项目根 | `./CLAUDE.md` | 本项目 | 只有一行 `Include: @./AGENTS.md` | 是 |
| 3 子目录 | `src/api/AGENTS.md` | 该目录 | monorepo 里前端一套、后端一套 | 是 |
| 4 本地私有 | `CLAUDE.local.md` | 本项目、仅自己 | 私有配置、本地路径、临时开关 | 否（进 `.gitignore`） |

从全局到具体依次读取。不同工具的文件名不一样，但**内容只该有一份**——规则放 `AGENTS.md`，`CLAUDE.md` 只做一层转接。两份都写，就是两份会分叉的内容。

子目录的规则只在 Agent 碰到对应目录的文件时才加载——**层级系统本身就自带渐进式披露**，不用额外设计。

## 写什么：WHAT / WHY / HOW

围绕三个维度写，基本不会漏关键内容：

- **WHAT**：项目是什么、技术栈、目录结构。
- **WHY**：每个模块的职责、为什么选这个方案。
- **HOW**：怎么跑测试、怎么构建、用什么包管理器。

一个精简但信息量足够的骨架：

```markdown
# 项目名：一句话说清楚这是什么
Next.js 14 项目，App Router + TypeScript。

## 常用命令
- `pnpm dev`：启动开发服务器
- `pnpm test src/xxx.test.ts`：跑单个测试文件，不要跑全量
- `pnpm typecheck`：改完代码必须跑一次

## 项目结构
- `/app` - 页面和路由
- `/lib` - 工具函数（跨模块共享的逻辑都在这，别重复造）
- `/prisma` - 数据库 schema，migration 文件不要手动改

## 重要约定
- 不要用 `--force` 推送，用 `--force-with-lease`
- 环境变量在 `.env.local`，不要提交
- 认证相关的改动，先读 `docs/auth-patterns.md`
```

> 那份原始骨架的最后一行写的是 `@docs/auth-patterns.md`。按下面的规则 4，这里的 `@` 要去掉：`@` 会在每次启动时把整份文档注入上下文，而这条规则想要的是“碰到认证改动时再读”。**照抄骨架时，凡是 `@` 都要过一遍规则 4。**

更完整的版本（小项目 / 团队项目 / monorepo）、`docs/` 目录结构、`.claude/rules/` 写法、多工具单一来源，见 `references/templates.md`。

## 七条写法规则

| # | 规则 | 反例 | 改成 |
|---|---|---|---|
| 1 | **命令写到精确语法** | “注意测试性能” | `` `pnpm test src/xxx.test.ts` `` |
| 2 | **只写它猜不到的** | TypeScript 基础语法、README 已有的介绍、linter 能管的风格 | 为什么这个目录不能碰、当年踩过什么坑、哪段看着冗余的逻辑是给老用户留的兼容 |
| 3 | **每个“不要”后面跟一个“应该”** | “不要用 `--force`” | “不要用 `--force`，用 `--force-with-lease`” |
| 4 | **详细文档用条件引用，不要 `@` 内嵌** | `@docs/tracking.md` | “涉及行为打点的改动，先读 `docs/tracking.md`” |
| 5 | **模块化，用路径限定作用域** | 把所有后端规范堆在根文件 | `.claude/rules/auth.md` + frontmatter `paths: src/auth/**` |
| 6 | **强调要克制** | 每条都写 `IMPORTANT:` | 只给反复被违反的那几条（通常 1–3 条，总数不超过 5 处）加 `IMPORTANT:` / `YOU MUST:` |
| 7 | **指定压缩时保留什么** | 长会话压缩后状态全丢 | “压缩时必须保留：修改过的文件列表、测试命令与结果、当前实现计划” |

展开说三处最容易踩错的：

**规则 2 的原因**：确定性的事交给确定性工具，更快更准，还不占指令预算。真正值得写的是**只存在于你脑子里**的东西——业务背景、历史决策、踩过的坑。

**规则 3 的原因**：只写“不要用 `--force`”，Agent 在需要强推时会卡住，或者自作主张用一个更糟的办法。给它替代路径，规则才闭环。

**规则 4 的原因**：`@path` 会在**每次启动时把整个文件嵌进上下文**——你以为在做披露，实际在做灌注。真实教训：一份几万字的打点文档被 `@` 进 `CLAUDE.md`，每个会话一启动就背着近 10K token，而一天里可能只有一两个任务跟打点有关。改成条件指引后会话立刻清爽。

唯一例外是跨工具的单一来源引用 `Include: @./AGENTS.md`——它指向的本来就是每次启动都会读的文件，不多花上下文，也免了第二份内容分叉。

**多工具团队**：别维护好几份重复内容。规则全放 `AGENTS.md`（它本来就是通用标准），其他工具的配置文件里只写一行引用：

```markdown
Include: @./AGENTS.md
```

一份内容，处处生效，改一处全部同步。

## 工作流

先判定模式，四条路互不相同：

| 模式 | 触发信号 | 主流程 |
|---|---|---|
| **A. 从零写** | 仓库里还没有指令文件 | 1 → 2 → 3 → 4 → 5 → 6 |
| **B. 体检重写** | 文件很长，或用户说“不听话” | 0 → 1 → 2 → 3 → 4 → 5 → 6 |
| **C. 单条规则失效** | 其他都对，就某条规则反复被违反 | 见“单条规则不生效怎么修” |
| **D. 定期维护** | 例行体检、文件几个月没动 | 见“维护” |

**0. 先跑体检**（模式 B/D）

```bash
python3 scripts/audit_agents_md.py --repo <仓库根>   # 路径相对于本技能目录
```

它给出可复核的初筛：行数/token 预算、规则条数、优先级通胀、`@` 内嵌成本、只有“不要”没有“应该”的规则、模糊表述、重复、与 README 的重叠、结构缺项、新鲜度。**输出是线索不是判决**，每一条都要回原文确认。

**1. 只读事实，不编**

写之前必须真的读：`package.json` / `pyproject.toml` / `Makefile` / `README` / CI 配置 / 目录结构。命令必须来自真实配置。

读不到就留占位符 `【待补充：测试命令】`，**不要编一个看起来合理的 `pnpm test`**。写错的命令会被直接照做，然后卡住或者跑错东西。

**2. 过筛子**

用“一条判断标准”里的一个主问题加三个筛子逐条筛。筛掉的不是丢掉，是**外移到 `docs/`**——外移时要记下“什么时候该读它”，这句话才是留在 `AGENTS.md` 里的东西。

**3. 定层级**

按“放哪里：四层”决定每条规则的位置。个人偏好别写进项目文件，团队约定别写进 `CLAUDE.local.md`。

**4. 按骨架写**

用 WHAT/WHY/HOW 组织，套用七条写法规则。写的时候时刻记着：**读者是一个刚入职、聪明、但完全没有背景的同事**。

**5. 跑预算检查**

再跑一次体检脚本，确认：≤ 300 行、≤ 2500 token（能到 100 行上下更好）、≤ 100 条规则、强强调词 ≤ 5 处且不超过规则数的 30%、`@` 内嵌 ≤ 500 token、没有“只有不要”的规则。

**6. 交付**

按 `references/templates.md` 的“体检交付格式”交付：体检结果、主要问题、改写后的文件、移走的内容、待补充清单。然后交代维护节奏（见“维护”）。

## 单条规则不生效怎么修

真实案例：全量测试要四分多钟，Agent 每次改完代码都习惯性跑 `pnpm test`，一等四分钟。加的规则是：

```markdown
注意测试的执行效率，避免不必要的全量测试。
```

**没用。** Agent 照样跑全量。

先别怀疑模型。把那条规则单独拎出来读一遍，问题有两个：

1. **位置**：它埋在一个两百多行文件的中部，前后全是同样口吻的“注意”和“避免”，很容易被淹没。
2. **不可执行**：“避免不必要的”——什么算必要？怎么避免？没说，它只能猜，猜的结果就是不听话。

改成：

```markdown
## 测试
- 跑测试用 `pnpm test <文件路径>`，只跑改动相关的文件
- 全量测试很慢（4 分钟+），避免全量测试，只在我明确要求时才跑
```

**两个变化**：模糊的形容词换成精确命令；“不要做什么”配上了“应该做什么”。当天生效，之后再没见它主动跑过全量。

**四步归因**，按顺序排查任何一条不生效的规则：

| 步 | 查什么 | 修法 |
|---|---|---|
| 1 | 位置——是否埋在长文件中后段，周围全是同质内容 | 提到前部，或单独成节 |
| 2 | 可执行性——读完知道具体跑什么命令吗 | 换成精确命令或明确判据 |
| 3 | 闭环——只有“不要”没有“应该”吗 | 补上替代路径 |
| 4 | 冲突——和另一条规则重复或矛盾吗 | 合并或删除一条 |

你总能找到优化点。找不到时的最后手段是加 `IMPORTANT:`，但那是止血，不是修复。

## 维护：把它当活文档养

这是大部分人做得最差的一步。

**`/init` 生成的内容恰好是最没价值的部分**——它写的都是能从代码推断出来的东西。真正值钱的架构决策和业务背景，只有你脑子里有。

值得学的做法：Claude Code 创始人 Boris Cherny 的 `CLAUDE.md` 只有约 2.5k token（一百多行），提交到 git，**每次 Claude 犯了一个他没拦住的错，就往里加一条**。这个文件在他那里是一个持续进化的错题本，撑起了他同时跑多个实例的日常。

错题本模式好在哪：

1. 每条都来自真实翻车，所以每条都是 Agent **猜不到的**；
2. 按需增长，不会一上来就写成百科全书；
3. 每条都有事故背书，三周后回头看也知道它为什么存在，不容易烂。

错题本条目这样写：

```markdown
- 改 `src/billing/` 下的任何文件后必须跑 `pnpm test src/billing`。
  （曾经改完只跑了 typecheck，漏掉一个金额取整的回归，线上多扣了一次钱）
```

**一增一减才平衡。** 每隔几周让 Agent 自己审一遍：有没有过时的内容？有没有冗余规则？对每一行问一个问题——**删掉这行，Agent 会不会犯错？不会就删。**

收个尾：这个文件的价值不由长度决定，由信噪比决定。**目录优于百科全书，精确优于全面，活文档优于一次性工程。**

## 交付前自检

- [ ] 行数 ≤ 300、token ≤ 2500（能到 100 行上下更好），规则条数 ≤ 100（硬上限 150）
- [ ] 每条命令都来自真实配置，没读到的用 `【待补充】` 占位，没有编造
- [ ] 没有能从代码推断的内容（项目类型、目录清单、技术栈罗列）
- [ ] 没有确定性工具已经管的东西（缩进、格式、lint 规则）
- [ ] 每条“不要 X”都有“，用 Y”
- [ ] 没有 `@` 内嵌长文档，全部改成条件指引
- [ ] 强强调词 ≤ 5 处且不超过规则数的 30%，只给了真正反复被违反的那几条
- [ ] 文件里有明确的外部入口（什么时候读 `docs/` 哪个文件）
- [ ] 跨工具场景下只有一份内容，其他配置文件是引用
- [ ] 向用户交代了维护节奏（犯错就加一条、定期做减法）

## 边界

- 这个 Skill 管**给 Agent 看的启动指令**。写 README、API 文档、设计文档不在范围内——它们是 `AGENTS.md` 指向的目标，不是它本身。
- 规则内容必须来自用户的真实项目。没有任何依据的“最佳实践”不要往里写，那只是把通用噪音换成了具体噪音。
- 用户坚持要写长文件时，照做，但把预算和代价讲清楚：可以从“至少把 `docs/` 抽出去、根文件只留索引”开始。
