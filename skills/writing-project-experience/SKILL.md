# 仓库 → 项目经历

把一个 git 仓库里的客观证据，转化为一段能放进简历、也经得起面试追问的项目经历。

## 三条底线（所有决策都回到这里）

1. **每句话都可追溯。** 面试官会顺着简历往下问。写下的每个动作、技术点、数字，都必须能指回某个 commit、PR、文件或用户的明确陈述。写得平淡不会出事，写了经不起追问的内容会。
2. **个人和团队分开。** 仓库是团队的产物，简历要回答的是“你做了什么”。项目整体的规模与成果不能算成个人功劳。
3. **缺失就是缺失。** git 里没有业务背景、线上效果、会议与决策、非代码工作。这些只能来自用户，模型不能“合理补全”。

反过来也要避免矫枉过正：有证据的亮点要写出具体做法（用了什么方法解决什么问题），含糊的“负责后端开发”同样没有价值。

## 工作流

1. 确认输入与身份
2. 采集证据
3. 归属个人贡献
4. 提炼主线并组织叙事
5. 处理信息缺口
6. 撰写
7. 自查并交付

### 第 1 步：确认输入与身份

需要两样东西：**仓库**（本地路径、已上传的代码，或可克隆的链接）和**“你是谁”**（git 姓名/邮箱/GitHub 用户名，允许多个别名）。

- 用户没说明身份时，先运行脚本不带 `--me` 列出贡献者，请用户指认。**不要猜**：在多人仓库里认错人，整份经历都会作废。
- 用户的自述与 git 证据冲突时（例如声称“整个项目是我做的”但贡献者有多人），以证据为准，并如实指出差异，不要迎合。
- 可选信息：目标岗位/JD、篇幅（精简/标准/详述）、保密要求。没给就用默认（标准版，语言跟随用户），不要为此多轮追问。

### 第 2 步：采集证据

先跑脚本拿到结构化摘要（路径相对于本技能目录）：

```bash
python scripts/collect_evidence.py <repo> --me "<姓名/邮箱片段>" [--me ...] --out evidence.json
# GitHub 仓库且 gh 已登录时，追加 --gh-user <用户名> 以获取 PR / Issue / 评审记录
```

脚本只给出可统计的事实和线索。接着你必须自己读：

- **README / docs / CHANGELOG / CI 配置 / Dockerfile**：项目定位、功能、已有的指标、部署方式。
- **模块归属与 blame 表中靠前的文件**：读真实代码，并用 `git show <hash>` 看关键提交的 diff。提交信息经常夸大或过于简略，**以 diff 为准**。
- **PR 描述、Issue 讨论、评审评论**：动机、方案取舍、他人评价。这些是“为什么这么做”的最佳来源。

各类证据能证明与不能证明的：

| 来源 | 能证明 | 不能证明 |
|---|---|---|
| 代码 / diff | 做了什么、怎么实现的 | 为什么做、效果如何 |
| commit message | 当时的意图 | 实际效果（常被夸大或过简） |
| PR / Issue | 动机、方案取舍、协作关系 | 最终线上结果 |
| README / CHANGELOG | 项目定位、功能、可能的指标 | 个人归属 |
| 测试 / benchmark / CI | 质量与性能的客观数据 | 业务价值 |
| 用户口述 | 背景、角色、成果 | 需在附录标注为“用户提供” |

不要通读整个仓库。让证据告诉你哪里重要，再深入。脚本的细节、手动取证命令与特殊仓库情形见 `references/evidence-playbook.md`。

### 第 3 步：区分个人贡献与团队协作

这是整份经历最容易出错的地方。按下面四步做。

**3.1 先解析身份。** 同一个人常有多个邮箱（公司邮箱、GitHub noreply、旧邮箱）。用脚本的“可能的别名”提示向用户确认，必要时合并统计。

**3.2 按信号强弱判断，不看单一数字。**

| 强度 | 信号 |
|---|---|
| 强 | 本人 commit；本人发起并合入的 PR；HEAD 中仍存活的、由本人写的代码（blame）；本人撰写的设计类 Issue/文档 |
| 中 | Co-authored-by 署名；作为 committer 合入他人提交；对他人 PR 的实质性评审意见；本人负责的模块目录 |
| 弱 | 仅修改过某文件几行；仅出现在提交讨论里；只有目录归属而无本人提交 |

提交数和代码行数只是线索，不是结论：一行关键的并发修复可能比一千行脚手架更重要。判断时看**该工作在项目中的位置与难度**，而不是数量。

**3.2.1 先去噪再统计。** 排除合并提交、依赖锁文件、构建产物、生成代码、批量格式化/重命名、数据文件、bot 提交（脚本已处理大部分；格式化与重命名需要你读提交确认）。

**3.3 把贡献归入层级，用对应的措辞。**

| 层级 | 典型证据 | 措辞 |
|---|---|---|
| 独立负责 | 模块内存活代码绝大多数（约 70% 以上）为本人所写；设计类 Issue/PR 由本人发起；他人很少改动 | 独立设计并实现… / 负责… |
| 主导 | 多人参与的模块中有**决策层面的证据**：方案类 PR/Issue 由本人发起、评审他人对该模块的 PR、做的迁移或重构被他人沿用 | 主导…的方案设计与落地 |
| 核心参与 | 占模块改动相当份额（约 30%–70%），能指出具体子功能 | 参与…，负责其中… |
| 参与 / 协助 | 少量提交、缺陷修复、评审、文档 | 参与… / 协助完成… |

百分比是经验线索，不是硬性门槛。**“主导”“从 0 到 1”“架构设计”“技术负责人”需要决策证据**，仅凭提交多不够。拿不准时降一级措辞，并把理由写入附录让用户决定。

**3.4 在文字里把团队和个人写开。**

- 项目整体的背景、规模、用户量、团队成果属于“项目”，只出现在项目背景与成果部分，并明确标注是项目整体。
- 个人贡献条目里省略主语（中文简历惯例）。需要写协作时点明对象和分工，如“与前端同学约定流式协议并联调”，不要把对方的工作写成自己的。
- 结对或 Co-authored-by 的工作写成“与 X 协作完成”。
- 团队规模按**活跃的人类贡献者**统计（排除 bot 和一次性提交者），正文写成“团队约 N 人”，在附录注明统计口径并请用户确认，因为产品、测试、运维等角色不在 git 里。
- 本人占比低时照实写成“参与”，并把笔墨放在你确实做的那一块上。不要为了显得重要而扩大范围。

### 第 4 步：提炼主线并组织叙事

**先聚类，再选择。** 把本人的提交聚成若干“工作主线”：优先按 PR/Issue 关联，其次按目录与提交 scope，最后按时间邻近与主题。不要按 commit 流水账叙述。

**为主线排序**，综合考虑：影响面（是否在核心路径、被多少代码依赖）、技术含量（算法、并发、一致性、性能、架构变更）、个人占比、是否有可证实的结果、与目标岗位的相关度。通常选 **3–5 条**写入核心贡献，其余合并为一句“另包括……”。

**选择组织轴：**

| 轴 | 何时用 | 写法 |
|---|---|---|
| 按模块/能力（默认） | 项目含 2 个以上相对独立的领域；需要对齐 JD 的能力标签（后端、前端、AI、部署）；用户全程参与 | 每条贡献对应一个模块或能力，条内用“先…后…”带出演进 |
| 按时间/阶段 | 项目有清晰的演进（0→1、扩展、重构或性能治理）；用户中途加入或职责逐步扩大 | 按阶段分组，每阶段写目标与产出，体现成长与 owner 范围变化 |
| 混合 | 既有多个领域又有明显阶段 | 以模块为纲；时间只出现在项目头部和关键里程碑 |

每条核心贡献按“**问题/背景 → 做法 → 结果**”的顺序组织。结果必须有证据，没有就如实写成交付事实，不要编效果。

### 第 5 步：处理信息不足或缺失

按这个顺序处理：

1. **先在仓库里找。** README、Issue、PR、CHANGELOG、测试与基准文件里常有被忽略的线索。
2. **能推断的标注为“推断”**，不要写成既成事实。例如从依赖和代码看到使用了 Redis 缓存，可以写“引入缓存层”，不能写“降低延迟 X%”。
3. **集中向用户提问。** 一次问完，不超过 5 个，按重要性排序，每个附上为什么需要。**先交出带占位符的初稿，再附问题清单**，用户对着具体文字更容易补充。只有“身份未知”这一项会阻塞开工。
4. **仍缺就留占位符**，如【待补充：上线后的日均调用量】。绝不为了版面好看补数字。
5. **证据太薄时降级输出**，直接说明“仓库证据只够支撑以下几点”，并给出缩小范围的版本，不要硬凑完整结构。

常见缺口与处理：

| 缺口 | 处理 |
|---|---|
| 无项目背景/业务目标 | 只写 README 能支持的“做什么”；“为什么/为谁”向用户要，否则占位 |
| 无成果数据 | 写交付事实（已上线、已合入、覆盖场景数），指标用占位符，并告诉用户可以怎样测量 |
| 无 PR/Issue（或非 GitHub） | 说明缺失，改以 commit、代码与用户口述为证据，不推断评审与协作关系 |
| 提交信息低质（fix/update） | 以 diff 为准；表述保守一档 |
| 历史被 squash / 迁移 / 浅克隆 | 先尝试补全历史；仍不可得则声明归属不确定并请用户确认 |
| 非代码贡献（设计文档、运维、测试、带人） | git 看不到，向用户询问，写入时标注“用户提供” |
| 用户不在 git 历史里 | 不要强行写成他的贡献；确认是否用了别的账号，或工作不经由此仓库 |

标准追问清单（按需挑选）：项目为谁做、解决什么问题；你的角色与团队规模；是否上线、使用规模；可量化结果及测量口径（对比什么、怎么测的）；你认为最难的问题以及为什么这样解。

### 第 6 步：撰写

按“输出规范”一节写。动笔前先在心里建好**证据对照**：每条贡献 → 对应的 commit/PR/文件。对照表要在交付时附上。

### 第 7 步：自查并交付

逐句核对后再交付：

- [ ] 每条贡献都能在证据对照表里找到来源？找不到的删掉，或标为待确认。
- [ ] 动词与证据匹配？（“设计/主导/优化/从 0 到 1”见 `references/writing-guide.md` 的动词校准表）
- [ ] 所有数字都有出处（仓库、用户提供）和口径？没有的已改为占位符？
- [ ] 项目整体成果没有混进个人贡献？团队成员的工作没有被写成自己的？
- [ ] 技术栈只列了“仓库里确有使用且与本人工作相关”的技术？依赖清单里出现不等于用过。
- [ ] 没有从 star 数、仓库规模等间接信息推断用户量或业务影响？
- [ ] 没有泄露内部地址、客户名、密钥、未公开业务数据？若是公司仓库，提醒用户确认可披露范围。
- [ ] 语气克制，没有禁用词？篇幅在规定范围内？

## 防夸大与防虚构规则

这些规则用于约束你在撰写时的判断，原因都是同一个：用户要拿这份文字去面试。

**证据分级。** 内部为每条陈述标级：
- **A 已证实**：有 commit/PR/代码/文档直接支持。可以写入正文。
- **B 可推断**：由证据合理推出但无直接说明（如从依赖推断用了某组件）。只在措辞保守时写入，并列入附录待确认。
- **C 需用户确认**：来自缺口或你的猜测。**不得**写入正文，只能作为占位或问题。

**数字。** 只使用来自（a）仓库（README、CHANGELOG、benchmark、测试、PR 描述）或（b）用户明确提供的数字。每个数字要带三要素：指标、对比基线、口径或来源。提交数、新增行数可作为事实使用，但价值很低，不要当作亮点，更不要写成“代码量 5 万行”这样的头条。

**动词。** 动词强度必须与证据强度匹配。“优化”需要有前后对比或至少明确针对某个瓶颈的改动；“设计”需要设计层面的证据；“负责”需要持续的所有权。校准表见 `references/writing-guide.md`。

**技术栈。** 区分“依赖里有”和“本人用过”。只写本人改动涉及或能证明使用的技术。

**规模与影响。** 不从 star 数、fork 数、仓库体量推断用户量、并发或营收。“高并发”“高可用”“海量数据”这类词没有数据支持就不用。

**他人与上游。** Fork 的项目要区分上游已有的代码与本人在 fork 点之后的提交，写成“基于 X 二次开发”。不要把开源上游的功能写成自己的。

**宁可保守一档。** 在“独立负责”和“核心参与”之间犹豫，就选后者，并在附录说明依据，让用户自己决定是否升级。用户决定升级时，在附录记下“用户确认”。

## 输出规范

### 交付物

两部分，**不要混在一起**：

- **A. 项目经历正文**：可以直接复制进简历的内容。正文里只保留成品文字和【待补充】占位符，不夹带来源批注、证据编号或“待确认”字样，这些都放附录。
- **B. 附录（仅给用户看，不进简历）**：证据对照表、归属判断说明、待补充/待确认问题、面试可能被追问的 2–3 个点。

### 正文结构

```
### {项目名称}｜{角色}｜{起止时间}｜{团队规模}
**技术栈**：…（仅本人使用且有证据的技术）
**项目背景**：1–2 句。做什么、为谁、解决什么问题。描述项目整体，来源写入附录。
**个人职责**：1–2 句。负责的范围与边界，例如“负责 A、B 模块；C 模块由同事负责”。
**技术方案**：2–3 句或要点。整体架构与关键选型，及选型理由（有证据时），写本人参与部分的方案。
**核心贡献**：
- 动词 + 做法 + 结果/影响（3–5 条）
**成果影响**：1–2 条。有数据则写数据（含口径与来源）；无数据则写可验证的交付事实；缺失处用【待补充：…】。
```

没有证据支撑的小节宁可缩短，也不要为了凑结构而扩写。

### 篇幅

| 版本 | 字数 | 条数 | 适用 |
|---|---|---|---|
| 精简版 | 约 120–200 字 | 核心贡献 3–4 条，其他小节合并为 1–2 句 | 简历空间紧张 |
| **标准版（默认）** | 约 300–500 字 | 核心贡献 3–5 条，每条不超过 2 行 | 常规简历、作品集 |
| 详述版 | 约 600–1000 字 | 每条贡献可展开问题/方案/结果 | 面试讲稿、个人网站 |

不论哪个版本，附录要简短，只列要点与来源。

### 语气与措辞

- **克制、事实陈述。** 用动词开头，写做了什么、怎么做、得到什么。
- **中文简历惯例：省略“我”**；团队成果以“团队/项目”为主语。
- **过去时事实**，不写愿景和决心。
- **具体优先于形容。** 用技术细节和数据代替“出色”“深入”“极致”等评价词。
- **术语准确**：保留通用英文术语（如 RAG、SSE、Redis），中英文之间加空格。
- 语言跟随用户；仓库是英文而用户用中文时，输出中文，技术名词保持原文。
- 禁用与慎用词见 `references/writing-guide.md`。

### 文件交付

默认直接在对话里给出 Markdown。只有用户明确要 Word / PDF 等文件时，才按当前环境中对应的文档类技能生成。
