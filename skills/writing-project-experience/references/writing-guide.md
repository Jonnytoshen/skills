## 1. 动词校准表

动词的强度必须与证据的强度匹配。证据不够时，**降级用词**，不要升级证据。

| 动词 | 至少需要的证据 | 证据不足时改用 |
|---|---|---|
| 设计 | 设计类 Issue/PR/文档，或可见的方案取舍；模块的整体结构由本人提交 | 实现 |
| 主导 | 决策层面的证据（方案类 PR/Issue 由本人发起、评审他人对该模块的 PR）且有他人参与 | 负责 / 参与 |
| 独立完成 | 模块内几乎全部代码由本人写，他人极少改动 | 负责 |
| 从 0 到 1 | 本人在项目或模块最早的提交中，并奠定了主体结构 | 参与…的搭建 |
| 负责 | 对该模块有持续的所有权（长期提交、修复与维护） | 参与 |
| 优化 | 针对明确瓶颈的改动，最好有前后对比 | 调整 / 改进（同时写清做了什么） |
| 重构 | diff 呈现结构性改动且行为保持（有测试更佳） | 调整 |
| 解决 | 有对应 Issue/缺陷及其修复 | 修复 |
| 推动 / 落地 | 被合入且有上线证据 | 完成 / 提交 |
| 带领 / 指导 | 用户提供，或有评审记录；git 难以证明 | 不使用 |
| 建立规范 / 体系 | 有文档且有被他人遵循的证据 | 编写 |
| 提升 X% | 有来源数据，含基线与口径 | 删去数字，写做法 |

## 2. 量化表述规则

一个能写进简历的数字需要三样东西：**指标**（测的是什么）、**基线**（和什么比）、**口径**（怎么测的，来源是什么）。

- “hit@5 由 0.71 提升至 0.84（200 条评测集）”：完整。
- “准确率提升 20%”：缺基线与口径，不使用。
- 来自仓库的数字，在附录里写出出处（文件/PR/commit）；来自用户的数字，在附录标注“用户提供”。
- **提交数、新增行数**是事实，但不体现价值，不当作亮点；若要使用，写清统计口径，且放在次要位置。
- 项目整体的数字（用户量、QPS、准确率）属于项目，不属于个人。写在背景或成果里，并标明是项目整体。
- 找不到数字时，写**可验证的交付事实**（“已合入主干”“覆盖 N 类文档格式”），并用占位符提示补充，例如【待补充：缓存命中率及统计口径】。同时告诉用户怎么测：用评测集跑改动前后对比、用压测工具测延迟分位数、用监控面板取命中率。

## 3. 夸大 → 克制 改写对照

| 夸大/空泛的写法 | 问题 | 克制且可追溯的写法 |
|---|---|---|
| 精通 RAG 全链路，打造行业领先的智能问答平台 | 评价词、无法验证 | 实现向量 + BM25 混合检索与重排，在 200 条评测集上 hit@5 由 0.71 提升至 0.84 |
| 主导系统架构设计 | 只做了接口实现，无决策证据 | 实现对话 API 与 SSE 流式输出 |
| 大幅提升系统性能 | “大幅”无数据 | 为高频问题增加 Redis 语义缓存（PR #27）；命中率【待补充】 |
| 负责整个后端 | 范围夸大 | 负责对话与检索模块（`backend/api`、`backend/rag`） |
| 支持百万级用户的高并发架构 | 无任何规模证据 | 删除；或【待补充：实际用户量与峰值并发】 |
| 使用 Kubernetes 实现高可用部署 | 仓库只有 Dockerfile | 编写 Dockerfile 与 CI 构建流程 |
| 参与了系统的开发工作 | 空话，无信息量 | 写出你参与的具体模块和做法 |
| 团队协作良好、沟通能力强 | 不可验证 | 与前端约定流式事件格式并完成联调 |
| 独立完成全部功能 | 与 git 里的多位贡献者冲突 | 独立完成检索模块；其余模块与 X、Y 协作 |

## 4. 禁用与慎用词

**禁用**（无法验证，面试官视为空话）：精通、卓越、极致、行业领先、颠覆、首创、独创、完美、赋能、打造闭环、全方位、深度参与、大幅、显著（无数据时）。

**慎用**（必须有对应证据才可使用）：
- 高并发、高可用、海量、大规模、分布式：需要规模数据或架构证据。
- 从 0 到 1、主导、架构、核心、负责人：见动词校准表。
- 熟练、掌握、深入理解（用于技术栈列表）：技术栈只列事实，不加程度词。
- 参与…相关工作、协助…等：太空泛，要写出具体做了什么。

## 5. 缺证据时的写法

占位符统一格式：`【待补充：具体要补什么】`，写明所需信息与口径，方便用户直接填。

```
成果影响：
- 检索效果：hit@5 由 0.71 提升至 0.84（PR #12，200 条评测集）
- 使用情况：【待补充：使用部门、日均调用量】
```

证据太薄时直接说明并缩小范围：

> 仓库中本人的有效提交仅集中在 `backend/api` 下的 6 次，证据只够支撑“实现对话接口与流式输出”这一条。以下是据此写出的简短版本；若还有未体现在仓库里的工作（设计、评审、联调、线上排障），请告诉我，我再补充。

## 6. 精简版与详述版模板

### 精简版（约 120–200 字）

```
### {项目名}｜{角色}｜{时间}
{一句话项目背景与个人职责，标注团队规模}。技术栈：{…}。
- {动词 + 做法 + 结果}
- {动词 + 做法 + 结果}
- {动词 + 做法 + 结果}
```

背景、职责、方案合并成一两句，不单独设小节；成果并入对应条目。

### 详述版（约 600–1000 字）

在标准版基础上，每条核心贡献展开为三句：

```
- {贡献标题}
  - 问题：{遇到什么问题/约束，证据来源}
  - 做法：{选型、关键实现、为什么这样做（有 PR/Issue 论述时引用）}
  - 结果：{可验证的结果，含口径}；{协作对象与分工}
```

技术方案一节可增加“方案取舍”：考虑过哪些备选、为什么没选（仅限有证据时）。详述版用于面试讲稿或个人网站，不要原样放进简历。

## 7. 完整示例

> **这是虚构示例，只用来展示格式和“陈述 ↔ 证据”的对应关系。** 其中的项目、数字和人名都是演示用的；真实输出里每个数字都必须来自仓库或用户。

**场景**：用户 Zhang San（`zs@corp.com`，另有 GitHub noreply 邮箱，已确认为同一人），仓库 `docqa`，git 活跃人类贡献者 3 人：Zhang San（后端）、Li Si（前端）、Wang Wu（部署）。

### A. 项目经历正文（标准版）

### DocQA 企业知识库问答服务｜后端开发｜2025.03–2025.06｜团队约 3 人

**技术栈**：Python、FastAPI、Milvus、Redis、Docker

**项目背景**：面向企业内部文档的问答服务。用户以自然语言提问，系统从文档库中检索相关内容并生成带出处的回答。

**个人职责**：负责对话 API 与检索模块（`backend/api`、`backend/rag`）。前端页面由 Li Si 负责，部署流水线由 Wang Wu 主要负责，本人参与联调与构建脚本编写。

**技术方案**：采用“检索 + 生成”架构：文档分块后向量化存入 Milvus；查询时并行执行向量检索与 BM25 检索，合并后经重排模型筛选，再交给 LLM 生成回答，并通过 SSE 流式返回。

**核心贡献**：
- 实现向量 + BM25 混合检索与重排流程，并在 200 条评测集上做改动前后对比，hit@5 由 0.71 提升至 0.84
- 实现对话接口的 SSE 流式输出，与前端约定事件格式并完成联调
- 为高频重复问题增加基于 Redis 的语义缓存；上线后命中率约 30%
- 编写服务的 Dockerfile 与 CI 构建流程，与部署同事协作完成容器化
