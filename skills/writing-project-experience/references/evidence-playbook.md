## 1. 脚本选项与输出解读

```bash
python scripts/collect_evidence.py <repo> [选项]
```

| 选项 | 作用 |
|---|---|
| `--me <片段>` | 本人的姓名/邮箱/昵称片段，大小写不敏感，可多次传入。不传则只列贡献者 |
| `--out <file>` | 输出完整 JSON（含全部提交清单） |
| `--path <dir>` | 只统计子目录，适用于 monorepo；可多次传入 |
| `--range <a..b>` | 限定提交范围，适用于 fork（`upstream/main..HEAD`）或只看某个阶段 |
| `--since / --until` | 限定时间窗口 |
| `--all-branches` | 统计所有分支（默认只看当前 HEAD） |
| `--blame-files N` | 对本人改动最多的前 N 个文件做 blame；0 表示跳过（大仓库可调小） |
| `--gh-user <login>` | 用 gh CLI 拉取本人的 PR、Issue 与评审记录 |

**怎么读输出：**

- **贡献者表**：已排除合并提交；行数已过滤锁文件、构建产物、生成代码与数据文件。“可能的别名”提示同一人的多个邮箱，必须向用户确认后再合并。
- **模块归属表**：“占比”是本人改动行占该模块所有人改动行的比例。它描述的是**历史改动量**，不是现状，也不等于贡献价值。
- **blame 表**：HEAD 中仍存活的本人代码行，更接近“现在的代码里有多少是我写的”。仅覆盖本人改动最多的那些文件。
- **提交信息质量**：低信息提交（fix、update、修改）超过约 40% 时，提交信息不可靠，改以 diff 与用户补充为准。
- **警告区**：浅克隆、首次提交体量巨大（疑似历史导入）、存在 bot 提交、匹配到 0 条提交。出现警告时，先解决再往下做。

**脚本的局限：** 它统计的是 git 里能看见的东西。看不见的包括：评审与讨论（除非用 gh）、设计与沟通、排障过程、结对编程中没有署名的一方、线上效果。不要把脚本没有数据解读为“没有这项贡献”，应当询问用户。

## 2. 手动取证命令速查

```bash
# 本人在某模块的提交与改动文件
git log --author="<片段>" --no-merges --stat -- <path>

# 看某次提交的真实改动（以 diff 为准，不信 message）
git show <hash> --stat
git show <hash> -- <file>

# 某个函数/关键字最早是谁、何时引入的（pickaxe）
git log -S'<关键字>' --format='%h %an %ad %s' --date=short

# 某个文件的完整演进（含重命名）
git log --follow -p -- <file>

# 谁创建了某个文件或目录
git log --diff-filter=A --format='%h %an %ad %s' --date=short -- <path>

# 逐行归属：忽略空白、识别文件内与文件间移动
git blame -w -M -C <file>

# 全项目按人统计（合并别名可配 .mailmap）
git shortlog -sne --no-merges

# 沿主线看合入了哪些 PR（merge commit 流程）
git log --merges --first-parent --format='%h %s'

# 找引用了某个 PR/Issue 编号的提交
git log --grep='#123' --format='%h %an %s'

# 两个时间点之间的变化概览
git diff --stat <a>..<b>
```

GitHub（需要 `gh auth login`）：

```bash
gh pr view <N> --json title,body,author,reviews,additions,deletions,mergedAt,files
gh pr list --state all --author <login> --limit 200 --json number,title,state,mergedAt
gh issue view <N> --json title,body,author,comments
gh pr view <N> --comments        # 评审讨论
```

PR 描述与评审评论往往是“为什么这么设计”“考虑过哪些方案”的唯一记录，值得为每条候选亮点各读一两个。

## 3. 特殊仓库情形

| 情形 | 如何识别 | 处理 |
|---|---|---|
| **浅克隆** | 脚本警告 | `git fetch --unshallow`；无法获取时声明归属统计不完整 |
| **Squash merge** | 主线提交少而大，subject 带 `(#N)` | 作者通常是 PR 作者，但有些流程下是合并者；用 `--gh-user` 拉 PR 核对，以 PR 作者为准，并检查 committer |
| **Rebase / force-push** | author date 与 committer date 不一致 | 看时间线用 author date，不依赖 committer date |
| **历史迁移/导入** | 脚本警告首次提交体量巨大；提交者与内容明显不符 | 此前的真实作者无法从 git 判断，不要把导入者当原作者；请用户确认并说明只覆盖导入之后的贡献 |
| **Monorepo** | 项目只是某个子目录 | 加 `--path` 限定；技术栈、团队规模也只按该目录计 |
| **Fork 项目** | 有 upstream 远程；早期历史来自他人 | `git merge-base HEAD upstream/main` 找 fork 点，用 `--range <fork点>..HEAD`；写成“基于 X 二次开发”。若向上游提过 PR，那是另一类证据 |
| **同一人多个邮箱/账号** | “可能的别名” | 请用户确认后多次传 `--me` |
| **Bot 提交** | 脚本标记 | 不计入任何人 |
| **大规模格式化/重命名/搬迁** | 单次提交涉及极多文件 | 读该提交，排除或在归属说明里标注，不要当作实质贡献 |
| **提交了生成代码/第三方目录** | 行数异常大 | 脚本按常见路径过滤；自定义路径请手动排除并在归属说明中记录 |
| **非 GitHub（GitLab、Gitee、自建）** | remote 地址 | gh 不适用。用提交中的 `!N`/MR 编号，向用户索取导出或链接；拿不到就在附录标为缺失，不要推断评审关系 |
| **子模块** | `.gitmodules` | 子模块内的历史不在本仓库，需对子模块单独运行 |
| **用户匹配到 0 条提交** | 脚本警告 | 检查拼写；询问是否用过其他账号；也可能工作在别的仓库或属于非代码贡献。不要强行归属 |
| **结对/mob 编程** | Co-authored-by；同一人署名多个提交 | 只有一方署名时，另一方的贡献 git 看不到，需用户补充 |

## 4. 读代码时找什么

目标是找到**有技术含量且确属本人的工作**，并看清它“怎么做”，以便写出具体做法而不是空泛概括。

- **核心路径上的模块**：请求入口、数据流主干、被大量引用的抽象（`git grep` 看被引用次数）。
- **有取舍的地方**：缓存、并发控制、重试与幂等、一致性、限流、降级、批处理、索引与查询优化。
- **针对问题的改动**：关联 Issue 的修复、带复现用例的提交、“perf/fix”类提交及其测试。
- **工程化**：Dockerfile、CI 配置、迁移脚本、监控与日志、配置管理。
- **质量证据**：测试（尤其是本人新增的）、基准脚本、评测集与评测脚本。
- **设计痕迹**：ADR/RFC、设计 Issue、PR 里对方案的论述、接口定义与分层。

读的时候记下：**它解决什么问题 → 用了什么方法 → 是谁写的 → 证据在哪（hash/文件/PR）**。这四项就是后面证据对照表的一行。

## 5. 验证“成果”类说法

仓库里可能存在的、可作为成果证据的东西：

- README 或 CHANGELOG 中的性能/准确率数字（先确认是否与本人的改动有关）
- `benchmark/`、`eval/`、`scripts/` 里的基准或评测脚本与结果文件
- PR 描述里的前后对比（注意口径：数据集、环境、样本量）
- CI 中的覆盖率与通过情况

**判定规则：**

- 数字与本人改动明确对应、口径清楚 → 可用，附出处。
- 数字是项目整体的（如 README 的整体准确率）→ 只能放在“项目成果”，不能写成本人贡献。
- 数字来自用户口述 → 可用，在附录标注“用户提供”，建议用户保留测量依据。
- 找不到数字 → 用占位符，并告诉用户可以怎样测量（例如用评测集跑前后对比、用压测工具测延迟）。

## 6. 保密与可披露性

公司或客户仓库的内容不一定能写进简历。交付前检查：

- 内部域名、IP、仓库地址、客户名称、未公开的业务指标、密钥和账号。
- 项目名称是否可以公开；必要时改为通用描述（如“某电商平台的推荐服务”）。
- 提醒用户：能否披露取决于其与公司的协议，本技能无法判断。需要时向用户确认，并提供一份脱敏版本。
